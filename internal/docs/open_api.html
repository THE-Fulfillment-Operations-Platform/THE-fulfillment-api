Tổng quan

Khi hệ thống của bạn có đơn mới, gọi API này để đơn tự vào xưởng — không cần xuất Excel rồi import. Sau đó bạn hỏi lại API để biết đơn đang ở đâu và lấy mã vận đơn.

Địa chỉ gốchttps://fulfillment.bacgiangdecor.com/api/open/v1
Định dạngJSON, UTF-8. Gửi header Content-Type: application/json.
Xác thựcAPI key do xưởng cấp, gửi trong header.
Đặc tả máy đọcopenapi.yaml (OpenAPI 3) — nạp được vào Postman, Insomnia.

Mọi câu trả lời dùng chung một khung:

// Thành công
{ "success": true, "data": { ... } }

// Thất bại
{ "success": false, "error": { "code": "MÃ_LỖI", "message": "Mô tả", "details": [ ... ] } }

Hãy xử lý theo mã HTTP và error.code. Câu chữ trong message có thể thay đổi.

Bắt đầu nhanh

  1. Xin API key từ xưởng. Key có dạng ffm_…, chỉ hiện một lần lúc tạo — lưu vào nơi cất bí mật của hệ thống bạn.
  2. Thử key: 
    curl https://fulfillment.bacgiangdecor.com/api/open/v1/ping \
  -H "Authorization: Bearer ffm_KEY_CỦA_BẠN"
    Trả về tên seller của bạn là key đúng.
  3. Gửi đơn đầu tiên: 
    curl -X POST https://fulfillment.bacgiangdecor.com/api/open/v1/orders \
  -H "Authorization: Bearer ffm_KEY_CỦA_BẠN" \
  -H "Content-Type: application/json" \
  -d '{
    "order_id": "ETSY-3391820455",
    "shipping": {
      "name": "Jane Doe",
      "address1": "1 Main St",
      "city": "Saint Paul",
      "province": "MN",
      "zip": "55112",
      "country": "US",
      "phone": "+1 651 555 0100"
    },
    "items": [
      {
        "sku": "ASK-3L-ONM-5-X-5",
        "quantity": 2,
        "mockup_url": "https://cdn.example.com/mockups/3391820455-1.png",
        "design_url": "https://cdn.example.com/designs/3391820455-1.png"
      }
    ]
  }'
  4. Tra đơn bằng chính order_id của bạn: 
    curl https://fulfillment.bacgiangdecor.com/api/open/v1/orders/ETSY-3391820455 \
  -H "Authorization: Bearer ffm_KEY_CỦA_BẠN"

Xác thực

Mỗi request phải mang API key, theo một trong hai cách:

Authorization: Bearer ffm_KEY_CỦA_BẠN
// hoặc
X-API-Key: ffm_KEY_CỦA_BẠN
  • Một key thuộc về đúng một seller. Đơn tạo bằng key nào thuộc seller của key đó — không có trường nào để chọn seller khác.
  • Chỉ gọi API từ máy chủ của bạn. Đừng để key trong ứng dụng di động hay mã chạy trên trình duyệt.
  • Lộ key thì báo xưởng thu hồi và cấp key mới. Key bị thu hồi ngừng hoạt động gần như ngay lập tức.

Mỗi lần gọi tạo một đơn. Đơn vào hàng chờ xưởng duyệt rồi mới sản xuất.

Gửi lại không sợ trùng đơn

Tạo đơn là idempotent theo order_id. Gửi lại một order_id đã gửi thì API trả về đúng đơn đã tạo, không tạo đơn thứ hai.
Mã HTTPdata.createdNghĩa là
201trueVừa tạo đơn mới.
200falseorder_id này đã có. data.order là đơn cũ, không thay đổi gì.

Vì vậy khi gặp timeout, mất mạng hay lỗi 5xx, cứ gửi lại nguyên request (nên cách nhau vài giây, tăng dần). Cả 200 và 201 đều nghĩa là đơn đã nằm trong hệ thống xưởng.

API không sửa đơn. Gửi lại cùng order_id với nội dung khác thì đơn cũ vẫn giữ nguyên. Cần sửa hoặc huỷ đơn đã gửi, xem Hỏi đáp.

Đơn bị từ chối

Sai ở bất kỳ trường nào thì cả đơn không được tạo. API trả 422 và liệt kê mọi lỗi cùng lúc:

HTTP/1.1 422 Unprocessable Entity

{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Đơn chưa hợp lệ: 2 lỗi — xem error.details",
    "details": [
      { "field": "shipping.country", "code": "REQUIRED",      "message": "Thiếu shipping.country" },
      { "field": "items[0].sku",     "code": "SKU_NOT_FOUND", "message": "SKU không có trên hệ thống của xưởng — ..." }
    ]
  }
}

field là đường dẫn tới trường trong body bạn gửi; items[0] là dòng sản phẩm đầu tiên.

Tra đơn

Một đơn

GET/orders/{order_id}

Tra bằng order_id của bạn, hoặc bằng code của xưởng. data là đơn, cùng cấu trúc với data.order ở trên.

  • Nhớ URL-encode order_id. Nếu mã chứa dấu /, dùng GET /orders?order_id=….
  • Không có đơn: 404, error.code = ORDER_NOT_FOUND.

Vận đơn — tracking

Là null cho tới khi đơn có mã vận đơn. Sau đó:

"tracking": {
  "number": "9400111899223344556677",
  "status": "IN_TRANSIT",
  "detail": "Arrived at USPS Regional Facility",
  "location": "JAMAICA, NY",
  "updated_at": "2026-10-06T02:11:00Z",
  "delivered_at": null
}

tracking.status nhận một trong: PENDING, PRE_TRANSIT, IN_TRANSIT, OUT_FOR_DELIVERY, PICK_UP, DELIVERED, UNDELIVERED, EXCEPTION, EXPIRED, CANCELLED; rỗng khi chưa có lượt quét nào.

Để đồng bộ trạng thái, gọi lại định kỳ 15–30 phút một lần cho các đơn chưa DELIVERED/CANCELLED/REJECTED. Dùng GET /orders?status=… để lấy cả trang thay vì hỏi từng đơn.

Giới hạn

  • 120 request/phút cho mỗi key. Vượt thì nhận 429.
  • Tối đa 100 dòng sản phẩm một đơn.
  • Danh sách đơn: tối đa 100 đơn một trang.
  • Chỉ hỗ trợ HTTPS.

Hỏi đáp

Sửa hoặc huỷ đơn đã gửi thế nào?

Bản v1 chưa có API sửa/huỷ. Đăng nhập cổng seller để huỷ hoặc gửi yêu cầu huỷ, hoặc liên hệ xưởng. Đừng gửi lại đơn với order_id mới để "sửa" — xưởng sẽ sản xuất cả hai.

Tôi không có mã SKU của xưởng?

Xưởng gửi bạn danh sách SKU. Hệ thống của bạn cần một bảng đổi từ mã sản phẩm của bạn sang mã SKU của xưởng trước khi gọi API.

Một khách mua nhiều sản phẩm thì gửi mấy đơn?

Một đơn, nhiều dòng trong items. Các dòng cùng đơn được xưởng gom và gửi chung một kiện.

Đơn tôi gửi có được sản xuất ngay không?

Không. Xưởng duyệt trước (PENDING_REVIEW), duyệt xong mới vào sản xuất (IN_PRODUCTION).

Có môi trường thử không?

Chưa có môi trường riêng. Khi thử, báo trước với xưởng và đặt order_id bắt đầu bằng TEST- để xưởng biết đó là đơn thử và xoá đi.
